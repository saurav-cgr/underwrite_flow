## Executive Summary

T042 extends `recover_document_bytes` from detecting only *missing* stored
bytes (Phase 10 / T040) to also detecting *present-but-corrupted* bytes, by
comparing the on-disk file's SHA-256 against the already-verified
`Document.content_hash`. This closes the FR-006 gap: a retried load can no
longer report `complete: true` while a stored file silently differs from
its source. The fix is minimal (7 changed lines in production code), reuses
the existing `storage.restore()` primitive from T040, and is covered by a
new integration test that corrupts a stored file in place and asserts the
retry restores exact source bytes. Full suite (558 tests) and targeted
integration suite pass; no blockers or warnings found.

## Correctness & Security Notes

- **Trust boundary respected**: `recover_document_bytes` only ever writes
  bytes that were already validated against the source record by
  `verify_document` earlier in `load_record` (i.e. `existing.content_hash`
  is trustworthy before this function runs). It cannot be used to silently
  paper over a genuine collision — a true content mismatch against the
  *source* record still raises `RecordCollision` upstream, unchanged.
- **Path safety unchanged**: `storage.restore()` (from T040) still routes
  through `UploadStorage._resolve()`, which rejects traversal outside the
  upload root — no new attack surface introduced here.
- **No unsafe data reaches output**: nothing in this diff touches
  `loader_output.py`'s sanitization chokepoint; the change is entirely
  storage-layer detection/repair, consistent with the existing "one shared
  chokepoint" pattern used for T038/T041.
- **Exception handling is correct**: `StorageValidationError` (missing file)
  and a hash mismatch (present-but-corrupt file) both fall through to the
  same `storage.restore()` call; no exception is swallowed silently, and no
  bare `except` is used.
